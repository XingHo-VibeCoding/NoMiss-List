# NoMiss List

不是帮你「记住要做什么」，而是告诉你「**现在该做什么**」——一个轻量的时间安排工具。
不设分类、不设标签、不设优先级；不做积分、不做连击、不主动弹窗。

---

## 怎么跑起来（运行说明）

**前提**：本机已装好 Node.js（项目环境里已有）。

1. 打开命令行（`Win + R` → 输入 `cmd` → 回车）
2. 进入项目文件夹：
   ```
   cd /d D:\项目文件
   ```
3. 启动本地服务器：
   ```
   node dev-server.js
   ```
4. 浏览器打开：
   ```
   http://localhost:8000
   ```

**停止服务器**：回到那个命令行窗口，按 `Ctrl + C`

**换端口**（8000 被占用时）：
```
node dev-server.js 8080
```
然后访问 `http://localhost:8080`。

> **为什么必须用 localhost，而不是直接双击 index.html？**
> 浏览器的「本地存储」按来源隔离：双击打开得到的是 `file://`，和 `http://localhost` 是两个互不相通的数据空间。
> 这三天都用同一个地址，数据才会待在同一个地方，不会莫名"消失"。

## 演示模式（看四种页面状态用）

四种状态里的「空」和「出错」，用真实数据很难凑出来——你不可能为了让页面报错，先把浏览器的存储弄坏。所以有一条只在网址里加参数才生效的路：

| 网址 | 你会看到 |
|---|---|
| `http://localhost:8000/` | 你自己的真实数据（平时就用这个） |
| `http://localhost:8000/?demo=mock` | **假数据**渲染的主视图（含一处故意安排的冲突） |
| `http://localhost:8000/?demo=loading` | **加载中**长什么样（停留约 1.2 秒后自动继续） |
| `http://localhost:8000/?demo=empty` | **空**状态（没有任何任务与课表） |
| `http://localhost:8000/?demo=error` | **出错**状态（真的走一遍出错处理，每张卡里都有说明和「重新试一次」） |

**三条保证**：
1. 去掉网址里的 `?demo=…` 刷新，立刻回到你的真实数据；
2. 演示模式下**所有写入都被拦下**（会明确告诉你"这一下没有生效"），碰不到你的真实数据；
3. 顶部会挂一条横幅，随时提醒你"现在看的不是真实数据"。

> 关于「加载中」：真实使用时本地读取几乎是瞬时的，这一帧几乎看不见。它真正有用的时候是阶段二接了云数据库——那时候等待是真实存在的，这段代码那时才真正生效。

## 项目结构

```
NoMiss-List/
├── index.html               入口：4 个视图的骨架
├── styles/main.css          全部样式
├── scripts/main.js          入口：视图切换（第 1 步）
├── scripts/storage.js       ★ 存储层：唯一碰「数据存在哪」的文件（第 2 步）
├── scripts/model.js         数据模型：字段补齐、默认值、校验（第 2 步）
├── scripts/views.js         渲染层：列表、详情、表单、提示条、建议 / 本周大局 / 今天的安排（第 3、5 步）
│   └ 内含两个可复用组件：`timelineRow`（一行）与 `fillTimeline`（一整块）——
│     「今天的安排」和「点某天展开」共用它们，只差一个日期参数
├── scripts/scheduler.js     ★ 计算层：空档 / 冲突 / 紧迫度 / 建议 / 今日分段（第 4 步，第 5 步已接上画面）
├── scripts/demo.js          演示模式：假数据 + 写入保护（只在网址带 ?demo=… 时生效）
├── dev-server.js            本地开发服务器（开发用，不属于产品功能）
├── README.md                本文档
├── AGENTS.md                项目协作规则
├── PRD.md                   产品需求文档
├── research.md              需求研究
└── TECH_DESIGN.md           技术设计
```

分层原则：`storage.js` 是唯一碰"数据存在哪"的文件；`scheduler.js` 是唯一的算术；两者都不碰画面。

## 第一版跑起来之后（Day 7 每日一问 · 本人回答）

**问题**：第一版跑起来的那一刻，和你原本想象的差在哪？

**本人回答（原话，未作改写）**：

> 「我觉得初步的安排已经有了，但是有很多细节的雏形需要再做一下。」

**整理，非原话**：主体（"安排"这件事）已经成形——今天该做什么、时间怎么排、哪两件事撞了，这些都在了；但**细节还只是雏形**，离"顺手好用"还有距离。换句话说：**功能轮廓达成了，使用质感没达成。**

**这条回答对项目的意义**：它把下一步的方向从"继续加功能"改成了"**打磨已有功能的细节**"。所以 Day 7 结束时的待做清单（见 `TECH_DESIGN.md` 第十四节 14.1）里，C 组专门留给"细节的雏形"，并且要求**动手前先把这些细节逐条变成可判断的说法**——否则它会一直停留在"感觉还差点"的状态。

> 本文档里的待做清单、验收缺口与验证状态，都以这里为起点。

## 四种处境里，哪种最容易被忽略（Day 8 每日一问 · 本人回答）

**问题**：四种页面状态里，你觉得哪种最容易被忽略？为什么？

**本人回答（原话，未作改写）**：

> 「我觉得四种处境中，在加载中比较容易被忽略，因为这种状态不容易被发现」

**整理，非原话**：

| 你说的 | 落到这里是什么 |
|---|---|
| 选的是「加载中」 | 四种处境（加载中 / 成功 / 空 / 出错）里，你挑了加载中 |
| 理由是"不容易被发现" | 它出现得太短、甚至压根不出现，所以**没人会注意到它漏了** |

**这条理由在技术上正好成立**：本地存储的读取几乎是瞬时的，所以「加载中」在正常使用中**根本看不见**——只有等你以后接了云数据库（阶段二）、等待变成真实的几百毫秒到几秒，它才会天天出现在你眼前。

**所以它属于"越容易被忽略、越值得提前做"的那一类**：因为它坏掉的时候你也看不见（页面会短暂空白或跳动），但用户能感觉到"卡了一下"。这也正是它现在的做法是**真加载态、为阶段二预留**，而不是随手转个圈的原因。

**这条回答对项目的意义**：它说明了"看不见的状态"为什么要专门做出来——**不是因为好看，是因为它一旦缺失，用户感受到的是"这个网页不太对"，却说不出哪里不对。**
